# Память проекта bb-kimicode-plugin

## Диагностика остановки Kimi, 3 ноября 2026

- В BB установлен независимый провайдер `kimi-code`; настройки `sourceConfig`, `model` и `maxContextSize` имеют значение `auto`. Kimi CLI на проверенном хосте — 2.4.0.
- В диагностическом треде использовалась модель `moonshot-cn/kimi-k3.1-pro` через Moonshot Platform (`https://api.moonshot.cn/v1`), а не маршрут подписки Kimi Code. В исходном и изолированном каталогах ей назначено окно 1 048 576 токенов. Последнее измерение BB: 110 460 токенов.
- В журнале этой сессии 2 ноября после выполнения SSH-команды встречался HTTP 429: организация превысила суточный лимит TPD 1 500 000 токенов. Были и отдельные ошибки RPM 3 запроса в минуту. После TPD 429 CLI находился в фазе `retrying`, watchdog отмечал отсутствие событий. Утром 3 ноября повторный запрос также получил TPD 429. Позднее в BB отдельно отмечен разрыв связи с host daemon; он не объясняет первоначальную остановку.
- Ручное сжатие контекста и показ квот в BB этим плагином пока не поддерживаются. Контекстное окно модели и суточная квота токенов — разные ограничения; точное время сброса квоты по журналу не установлено.
- Уточнение после замечания пользователя: более новый диагностический тред использовал ту же модель `moonshot-cn/kimi-k3.1-pro` и успешно получал ответы в 19:32 и 19:47 UTC 2 ноября, уже после первого TPD 429 старого треда в 18:58 UTC. В 19:48 UTC новый тред тоже получил TPD 429; последнее измерение его контекста — 28 100 токенов. Следовательно, утверждать, что квота тогда полностью блокировала все запросы и новые треды, нельзя. Вклад размера запроса или резервирования токенов остаётся гипотезой: алгоритм TPD-провайдера и актуальный доступный остаток не установлены. Публичная ошибка Kimi CLI MoonshotAI/kimi-code#1796 описывает аналогичное молчаливое ожидание после TPD 429; применимость к этой версии и установленному случаю требует отдельной проверки.

## Исправление обработки ошибок API, 3 ноября 2026

- После просьбы пользователя решить проблему добавлен `src/acp-guard.ts`: автономный ACP-посредник запускает настроенный Kimi CLI, сохраняет поток ACP и при `session/prompt → end_turn` проверяет только новую ограниченную часть (до 128 КиБ) `agents/main/wire.jsonl`. Если новая запись `turn.ended` содержит `reason=failed`, возвращает JSON-RPC error, который стандартный мост BB превращает в `provider.error` с завершением текущего запроса. Предыдущие ошибки сессии не должны затрагивать следующие сообщения. Поддержана задержка записи журнала до 500 мс. Неизвестная структура журнала сохраняет исходный ответ ACP.
- Установлены `KIMI_LOOP_MAX_ATTEMPTS_PER_STEP=1` и изолированные `[loop_control] max_attempts_per_step=1, compaction_max_attempts=1`, чтобы CLI не ждал молча длинный Retry-After. Теперь повтор выполняет пользователь после устранения ограничения; самостоятельные настройки Kimi вне плагина не меняются.
- Ошибки в BB содержат тип отказа (TPD, 429, доступ, баланс, иной HTTP-статус), но не сырой текст провайдера с идентификаторами аккаунта/ключа. TPD current показывается как `reported`, поскольку точная семантика счётчика не установлена.
- Посредник создаётся атомарно в host bridge-data с правами 600. Он запускается через Node текущего host bridge; в BB на Electron нужен явный `ELECTRON_RUN_AS_NODE=1`, поскольку стандартный ACP-мост очищает наследуемый флаг. Перед запуском собственно Kimi этот флаг удаляется. Для `provider/*` maintenance используется исходный executable Kimi, чтобы health проверял CLI, а не Node.
- Добавлены регрессии на TPD/503, сокрытие приватных данных, задержанную запись ошибки, отмену и успешный следующий запрос в той же сессии. Добавлен `npm run smoke:errors`: настоящий установленный CLI обращается только к локальному тестовому HTTP API с фиктивными ключами; первый ответ — 429 + Retry-After 3600, второй — успешный SSE. Подтверждены один API-запрос при отказе, ошибка в BB и успешное продолжение той же сессии. Проверено на Kimi CLI 2.4.0.
- Успешно прошли typecheck, 10 тестов, conformance стандартного BB bridge, сборка и проверка npm-упаковки. Для проверки упаковки используется `npm_config_cache=/private/tmp/bb-kimicode-npm-cache` из-за недоступного основного npm-кеша. Реальный CLI требует запуска вне песочницы из-за EMFILE на fs.watch.
- Локально установленный плагин (источник path на этот checkout) пересобран и перезагружен через `bb plugin reload kimicode`. Проверка в живом BB после учёта Electron вернула все 11 моделей с default `kimi-code/k3.1-pro`. Рабочие пользовательские треды не запускались, запросы к платному API при smoke не выполнялись. Публичный релиз и коммит пока не создавались.
- Сохранён текущий SDK pin 0.6.49 и минимальная совместимость; работающий BB имеет SDK 0.6.104, поэтому сборка выводит предупреждение об отличии версии. Обновление SDK не включено в этот узкий фикс.

## Динамический каталог подписки, 3 ноября 2026

- Пользователь подтвердил алгоритм обновления каталога и попросил реализовать. Его цель — использовать собственную подписку `kimi-code/k3.1-pro`, не отдельный Moonshot Platform API. Из-за похожих названий прежний выбор был неоднозначным.
- Проверен реальный `GET https://api.kimi.com/coding/v1/models` с подписочным ключом, прочитанным программно из `.env` без вывода ключа. HTTP 200 вернул шесть подписочных моделей с `limit.context`, `modalities`, `reasoning`, `tools`, названиями и усилиями рассуждения. Этот endpoint принимает ключ подписки, OAuth для каталога не требуется.
- Добавлен `src/subscription-catalog.ts`: получение полного каталога на хосте, строгая нормализация метаданных, проверка полноты и дублей, тайм-аут 10 секунд, ограничение ответа 1 МиБ, запрет redirect с ключом. Фиксированный список шести моделей полностью удалён из production-кода. Тестовые списки находятся только в fixtures.
- Кеш `subscription-catalog-<sha256(endpoint+key)>.json` находится в bridge dataDir. Ключ не записывается; кеш содержит только нормализованные метаданные и время успешного/последнего обновления. Запись атомарная, mode 600. Другой ключ или endpoint не используют старый кеш. TTL 15 минут; после неудачи повторы ограничены минутой, ручное обновление может обойти задержку. Некорректный/неполный ответ сохраняет предыдущий каталог и время; успешный пустой ответ действительно очищает подписочный список. Без успешного кеша ошибка discovery видна пользователю, догадок о моделях нет.
- `src/catalog.ts` строит подписочный config только из live/cache данных. Нативный sourceConfig даёт предпочитаемый default, но не переопределяет подписочные метаданные и не возвращает удалённые модели. Добавлен `includeExternalModels=false` по умолчанию. Отдельные API-модели и их credentials импортируются лишь при явном true. Метки: `· подписка Kimi Code` и `· API (provider-id)`. Устаревшие подписочные записи в picker дополнительно имеют `· кеш`; описание содержит исходное время получения.
- `host.ts` асинхронно подготавливает каталог и напрямую отвечает на `model/list` без запуска CLI. Перед start/resume/fork/turn проверяется стабильный ID: отсутствующая или отключённая модель отклоняется до запуска CLI, без подмены на другую модель/API. Для нетинкинговых моделей reasoningLevel не отправляется. `thread/stop` не ждёт каталога; счётчик отмены не позволяет запустить старый запрос после остановки во время fetch. Закрытый bridge не диспатчит поздние async-результаты.
- `server.ts` инвалидирует регистрацию каталога при запуске, смене настроек и каждые 15 минут через отменяемый background service. При новых probes хост загружает каталог; session requests также проверяют возраст кеша. Добавлена команда `bb kimicode models refresh [--machine host_id]`; без флага берётся хост текущего треда, иначе server host. Она обновляет generation, запрашивает список и выводит имена/время/ошибку без секретов. Таймер использует default import `node:timers/promises`, чтобы его можно было корректно проверить Node MockTimers.
- Проверено в живом BB: список содержит только шесть `kimi-code/...` с подписочными метками, default — `kimi-code/k3.1-pro`; `moonshot-cn/...` по умолчанию отсутствует. Ручное обновление успешно обновляет timestamp. Сам sourceConfig, сторонние провайдеры BB и credentials не менялись. Старые пользовательские треды не запускались и их model selection не переписывался.
- Проверки: typecheck, 15 offline tests, стандартный SDK conformance, отдельный bridge catalog/retirement/cancellation check, сборка и npm package check прошли. Добавлены тесты добавления/удаления моделей, обновления context/reasoning metadata, stale fallback, смены ключа, неполных/пустых ответов, dedup fetch, выбора execution host, реального срабатывания 15-минутного таймера через MockTimers и disposal.
- Реальные проверки: короткий прямой запрос подписочного API вернул HTTP 200 и ожидаемый маркер; полный путь BB bridge → Kimi CLI → `kimi-code/k3.1-pro` проверен в отдельных временных сессиях на Low и обычном High. High с настройками по умолчанию ответил успешно при повторе. Первый High smoke не ответил за 90 секунд, причина не установлена; нельзя объявлять устранёнными любые возможные задержки сервиса. Локальный smoke HTTP 429 + Retry-After 3600 и последующее восстановление той же сессии также прошёл после перехода на динамический каталог.
- Тестовый CLI исполнялся вне песочницы из-за известных fs.watch/EMFILE ограничений. Временные каталоги трёх живых smoke удалены после release; обычный smoke теперь сам удаляет свой временный home. Документация, skill, overview и Unreleased changelog актуализированы. Финальная локальная сборка перезагружена, публичного релиза и коммита пока нет. SDK остаётся на ранее совместимом pin 0.6.49; host SDK 0.6.104 даёт предупреждение при сборке, обновление зависимостей в задачу не включено.
- Финальная проверка ручного refresh сразу после reload выявила гонку запуска host bridge (`Provider "kimi-code" is not running`). Команда теперь делает до четырёх коротких повторов 250/500/1000/2000 мс только для этого состояния; ошибки API, включая 429, не попадают в этот retry. Добавлены регрессии для обоих случаев. Повторная живая проверка сразу после reload завершилась успешно: шесть подписочных моделей, свежий timestamp, error=null. После этого изменений runtime-кода не было.
